### Package and Runtime

### Parent Ingress and Unix Guard

The native route is untouched OpenCode OAuth fetch -> parent-owned raw HTTP ingress -> `node:http` Unix-socket streaming -> separate Bun worker -> real bridge authenticated HTTP/CONNECT proxy -> one fixed trusted HTTPS gateway. The parent never performs upstream CONNECT. One shared numeric-loopback, OS-assigned TCP port belongs to the parent process until exit; call `unref()` so idle ingress does not prevent natural exit. Maintain private per-instance random capability-to-worker routes. Native baseURL contains only `http://127.0.0.1:<port>/codex`, never a capability. Inject capabilities only for activated OpenAI inference via the proven private hook; strip them at ingress before forwarding. Keep worker-generated capability delivery private over the bounded ready protocol; register a route only after worker checks, discovery and model validation succeed.

The parent creates a short private directory with mode 0700 and verified ownership/no unsafe symlinks for each worker Unix socket. Workers listen only there, never on a native-facing TCP port. Validate socket paths against the parent-owned directory, not arbitrary ready-frame destinations. Other UIDs cannot replace the socket even if worker death falls between a liveness check and the parent's connect. On worker EOF/exit/helper failure, invalidate the route before any reconnect, abort upstream/Unix streams and release proxy secrets; return sanitized 503 where headers permit or close in-flight responses. Once removed, old/missing capabilities return 403 with no forwarding. Never restart an activated failed route or retry directly.

Instance disposal removes only its route and owned worker/socket/state-lock resources with bounded cleanup. It never closes the shared parent listener, even when the map is empty: cached native retries can still carry bearer credentials without invoking header hooks. The bound parent port prevents another UID from receiving those bytes after worker loss or instance disposal. Parent exit releases the port only when that native parent is gone; do not claim protection for external clients persisting credentials beyond parent lifetime. Same-user/root compromise is out of scope. Track and bound active sockets/streams without allowing idle connections to defeat process exit; do not accumulate shutdown handlers or close shared ingress per request. Required evidence covers parent lifetime, multiple instances, worker crash during connect, rejection of cached native retries, attempted other-UID reuse/private-directory access, bounded cleanup and natural exit. Design selection resolves the architectural question, not the verification gate.

Ingress must inspect raw HTTP method/target/Host duplicates/Origin before forwarding: only exact origin-form `POST /codex/responses`, expected numeric-loopback Host, no Origin, valid private capability. Reject absolute targets and Connection nominations of required native headers; remove relay/proxy/hop headers and Connection nominations in both directions. The worker fixes the gateway destination, regenerates Host, preserves original SNI/certificate verification, rejects all redirects, and alone holds proxy credentials. Preserve native auth/account/session headers opaquely, never inspect native credential storage or replace native auth fetch. Stream uploads/SSE with bounded backpressure and independent cancellation. Discovery uses the bridge proxy with its independent 10-second timeout and existing catalog/model validation. Failed setup leaves native configuration untouched, not fail-closed; after activation never direct-fallback. Ordinary gateway errors retain native retries through the same guarded route.

Refuse arbitrary directories even if user-owned; never recursively delete merely because settings name a path. If an active server owns the profile, require disconnect and full restart first. ## Goals / Non-Goals

**Goals:**
- Offer OpenCode-native setup for an independent Tailscale node without a system client or root.
- Preserve native OpenAI HTTP/SSE, auth headers, discovery validation, and model configuration.
- Keep ordinary installations and bridge-disabled startup independent of bridge availability.
- Make credential handling, state ownership, cleanup, failure boundaries, and support evidence explicit.

**Non-Goals:**
- ChatGPT OAuth implementation, OpenAI auth loaders, auth-file access, application token persistence, or API-key-provider changes.
- Native auth-fetch replacement, global fetch patches, private APIs, global proxy/environment mutation, arbitrary-destination reverse proxying, transparent direct fallback, or generic VPN/firewall behavior.
- Automatic publication, helper downloads/builds at runtime, universal platform support, or unverified native token-refresh claims.

## Decisions

### 1. Prove host integration before building the feature

Before full feature implementation, prove the reverse relay on the installed native host with a separately selected transport worker runtime using public baseURL and header hooks, without replacing the native loader or fetch. Record host embedded Bun separately from worker Bun; only the worker performs upstream CONNECT. Prove traversal including retries and streams, private-memory-only relay capability and proxy credentials excluded from config APIs/logs/telemetry/persistence, private non-transcript enrollment UI, and bounded helper/relay/provider disposal. The parent owns a `chat.headers` closure for capability injection; complete scoping and non-exposure remain gates despite preliminary fixture success. The baseURL contains no secret. Native ChatGPT login, refresh, persistence, and auth-header injection remain exclusively OpenCode-owned; login and refresh stay unproxied.

Do not invent an `options.proxy` field or assume a public downstream callback exists. Original tasks 1.1/1.5 remain historical inspection/no-go results. Revised direct fetch-adapter inspection also yields NO-GO at `16747470f976aca3d362ad730bcd3fe82ecc2c9a`: config hooks cannot capture native loader fetch, configured fetch overwrites it, and neither the core wrapper nor native Codex fetch exposes downstream composition. See evidence for source ordering and public-interface references. The separate-worker relay is a different architecture, not reversal of those findings. Installed-host, UI, and lifecycle proofs remain incomplete; broad feature implementation stops, while focused process/proof tasks may proceed. Installing standalone Bun does not upgrade the embedded runtime. External proxy configuration alone does not deliver managed setup UX.

### 1a. Separate transport worker and explicit runtime selection

Keep transport in a distinct child process in both runtime modes. Default to external Bun: accept a nonsecret explicit absolute executable path, or resolve `bun` from PATH once to an absolute executable path before launch. An explicitly selected path must not fall back to PATH if it fails. Embedded mode is explicit and launches the identical worker entrypoint with absolute `process.execPath` and child-only `BUN_BE_BUN=1`; do not mutate the parent environment. Do not switch modes automatically on missing executables, version/protocol mismatch, timeout, or smoke failure. Never invoke a shell, download a runtime, or assume a newer version is compatible. Settings may record only the runtime mode and nonsecret absolute executable selection, not credentials or proxy URLs.

Validate the actual selected executable's Bun identity/version and supported protocol, not its filename or the harness version. `VERIFIED_TRANSPORT_BUN_VERSIONS` accepts exactly 1.4.2; extension requires exact-version differential/native checks, never newer semver trust. Require bounded streamed HTTPS CONNECT and reader-cancellation smoke with verification enabled before activation. External worker 1.4.2 has now passed the five-scenario synthetic native subset; embedded 1.3.14 rejects its hello before startup bytes. No future external or embedded positive is verified. Switching runtime changes only executable selection, never process ownership or protocol. Current supervisor input requires absolute paths; the proof supplies harness `process.execPath` externally and native host `process.execPath` in embedded mode. The proposed consumer settings/PATH resolver is not implemented.

The parent supervises one worker per runtime/profile and retains the native OpenAI-only `chat.headers` capability closure. The worker owns relay, proxy connections, upstream TLS/streaming, and eventually the bridge/helper factory. Start with synthetic loopback proxy fixtures; provide the same worker factory boundary for the future bridge without loading or claiming Tailscale now. The native host still owns its native fetch and OAuth; its embedded Bun need not perform worker CONNECT.

Use private piped stdin/stdout with a versioned bounded JSON-lines control protocol, stdout exclusively protocol, and no inherited/raw helper or native logs on either output. Define and test finite byte/line, message-count, startup, shutdown, and backpressure bounds. Reject malformed, oversized, duplicate, out-of-order, or unknown messages with allowlisted errors, never raw payloads/exceptions. Drain stderr with a bound and discard raw contents rather than forwarding them. Pass only nonsecret executable/entrypoint arguments and a minimal nonsecret child environment; no relay/proxy/enrollment secrets in argv, env, config URLs, or persisted fixtures.

The implemented sequence is worker `hello` (protocol 1, actual Bun version), then exactly one parent `start` over private stdin only after hello validation, then one worker `ready` after smoke and independent proxied fixture discovery. Startup contains the fixed HTTPS loopback target and synthetic CA/key, not a parent-generated capability or proxy password. The worker generates the independent 32-byte random capability, creates private proxy credentials, and returns capability, validated numeric-loopback origin and matching runtime/protocol in `ready`. Single-worker protocol state correlates readiness; there is no parent capability echo. Native headers/bodies do not enter control messages. Complete production discovery/model validation and future bridge/private enrollment inputs remain deferred.

The child uses `--no-env-file --config=/dev/null`, worker-directory cwd and an environment containing only inherited PATH plus child-only BUN_BE_BUN in embedded mode. The parent bounds startup/control lines to 64 KiB and cumulative stdout/stderr separately to 512 KiB, drains/discards stderr, and strictly validates frames and allowlisted events. Worker input is capped at 128 KiB total and a 64 KiB line buffer plus newline. Startup timeout defaults to 10 seconds (validated 1-60000 ms); the native fixture selects 15 seconds and the worker has its own 15-second deadline. The smoke uses privately supplied fixture PEMs, streamed CONNECT and reader cancellation before readiness; OpenSSL generates disposable test certificates outside the worker, not an asserted production dependency. These limits and streaming checks do not prove full bounded-memory/backpressure stress requirements.

Supervise an explicit `close` request acknowledged by process exit, not an explicit `closed` frame. Parent shutdown invalidates readiness/capability immediately, waits 150 ms for graceful exit, then 150 ms after SIGTERM and 300 ms after SIGKILL. Worker cleanup has a one-second force-exit deadline. Unexpected EOF/exit or invalid protocol cannot trigger restart-in-place or runtime fallback. Actual-worker stdin EOF tests cover before startup and after ready. Parent-pipe EOF is a crash backstop, not proof native traffic has ceased; closure checks cannot protect cached retries. The stale relay-port gate in decision 5 remains unresolved.

### 2. Explicit configuration, separate enrollment

Use a versioned plugin-owned nonsecret settings document outside the checkout, under the user's platform application-config directory in an `opencode-aperture` namespace. Proposed fields are `version: 1`, `bridge: { enabled, hostname, stateDir, startupTimeoutMs }`, and the explicit nonsecret worker runtime mode/absolute executable selection from decision 1a; final settings/UX implementation remains deferred. `enabled` defaults to false and startup timeout defaults to 60000 ms. Validate types, nonblank hostname, absolute state path outside project/package trees, and a positive finite bounded timeout before launching. Define the upper timeout bound as 300000 ms. Reject unknown versions/fields rather than silently ignoring misspellings. Preserve the existing gateway environment precedence and origin validation; do not introduce unknown top-level `opencode.json` keys.

The OpenCode setup UI edits these nonsecret settings, shows the selected gateway and its trust implications, chooses persistent state, and offers browser enrollment or masked transient auth-key input. Browser URLs and keys must never pass through an LLM tool, chat transcript, command argument, shell history, or ordinary log. Authentication material is held only long enough to call the bridge. No auth key is written to settings or inherited into child environments. Ambient `TS_*` variables are not used. If the host lacks a demonstrably private UI, the feature is blocked, not replaced by a chat-based secret prompt.

Setup is explicitly user initiated, not a prompt from the initialization config hook. Headless startup reuses enrolled state and fails promptly with a sanitized setup-required diagnostic if enrollment is missing. Settings writes are owner-only and atomic; cancellation leaves saved configuration unchanged. Successful enrollment and nonsecret settings become active after an explicit OpenCode restart. Existing native OpenAI login remains a separate action.

### 3. Separate node identity from application identity

Persistent node state belongs in a dedicated absolute per-user application-state directory outside projects and packages, using the upstream owner-only directory/file checks and exclusive lock. The default is a single named profile; competing processes must report a state-lock conflict rather than share a helper or corrupt identity. Advanced separate state paths create independent nodes and must be clearly described as such.

Reuse enrolled state before requesting enrollment. The plugin does not inspect or serialize node key material; it delegates state handling to the bridge. Persisting this private Tailscale identity is the sole identity-storage exception. Enrollment keys, proxy credentials, login URLs, OpenAI tokens, and account IDs are never plugin-persisted.

Disconnect disables the saved bridge configuration for future startup and closes the current helper without deleting identity. It does not dynamically switch an active provider to direct traffic; restart is required to resume normal native routing. Forget-state requires explicit confirmation, a stopped/unlocked owned state directory, and safe path checks. It removes only that profile's local state; remote node/key revocation is a separate Tailscale action. Removal instructions explain both operations and never touch native OpenAI credentials.

### 4. Fixed-upstream reverse relay with untouched native OAuth

For the future bridge, after host gates pass and origin validation succeeds, the verified worker lazily loads the optional bridge and starts it with a bounded deadline. Discovery uses the original gateway URL through the worker's per-request forward proxy and its independent 10-second timeout, redirect rejection, response validation, and no retries. The worker prepares a relay bound exclusively to a numeric loopback address on an OS-assigned random port; the parent atomically activates OpenAI baseURL `http://127.0.0.1:<port>/codex` and scoped private header injection only after ready and complete setup/model validation. Current infrastructure proves this with synthetic fixtures only. No secret appears in the baseURL. Do not set baseURL to `bridge.httpProxyURL()`: that is an authenticated HTTP/CONNECT forward proxy, not the reverse relay.

The route is untouched native OpenCode OAuth fetch -> numeric loopback reverse relay -> bridge HTTP/CONNECT forward proxy -> fixed validated gateway `/codex/responses`. The relay originates upstream TLS using the original gateway hostname for CONNECT/SNI/certificate verification, never the loopback name and never disabled verification. Reject all upstream redirects without following or returning a redirect that native fetch could follow. Upstream destination is fixed from validated configuration, never derived from request URL, Host, headers, or body. No direct fallback is allowed. The bridge is not a tailnet-only destination firewall.

Generate an independent cryptographically random per-runtime relay capability, separate from proxy authentication. Inject it in a private runtime request header only for activated native OpenAI inference using a proven public hook, potentially a `chat.headers` closure. Never store it in URLs, provider options, configuration, config/provider API responses, transcripts, logs, telemetry, or persistent state. Other providers and OAuth login/refresh receive neither this header nor relay routing. Missing or incorrect capability is rejected before forwarding. A random port alone is not authentication; same-user process/memory compromise is not defended.

Accept only the exact origin-form `POST /codex/responses`, with the exact numeric-loopback Host authority and no Origin header. Reject other methods/paths, absolute-form targets, ambiguous/duplicate Host, and hostile Origin/Host requests before forwarding; do not normalize an abusive target into an accepted one. Strip the relay capability, proxy authentication headers, all hop-by-hop headers, and every header nominated by Connection on both request and response legs. If Connection nominates a required native header, reject rather than silently stripping required auth/session semantics. Regenerate upstream Host from the configured origin; bridge proxy authentication belongs only on the proxy leg. Native Authorization/account/session headers are forwarded unchanged as opaque header values, never parsed, persisted, or logged; no auth loaders or auth-fetch replacement are allowed.

Stream uploads and SSE responses with backpressure, bounded buffering and cleanup, independent cancellation, and abort propagation on either-side disconnect. Do not buffer complete bodies, add relay retries, or expose raw transport errors. Prove completion, tools, concurrency, redirect rejection, credential stripping, TLS failure, cancellation, and native retry scoping before claiming support.

### 5. Explicit lifecycle and failure boundaries

Use one owned bridge per plugin runtime/profile, not per request. Creation resolves proxy readiness, not gateway reachability. Keep it alive through complete response consumption; failed setup always closes a partially created bridge and leaves caller configuration unchanged. Avoid duplicate startup during repeated config application. Respect caller cancellation and the bridge's startup deadline.

Startup failures retain the established non-destructive contract: sanitized diagnostics, unchanged native OpenAI configuration, and unrelated providers usable. This explicitly means native direct OpenAI traffic can remain available; this feature is not fail-closed at startup.

After successful activation, helper failure or disconnect moves the relay into a rejecting state within a bounded deadline, aborts upstream work, and invalidates/releases proxy credentials without attempting another connection to a potentially reused proxy port. Keep the relay listener bound and rejecting until the native runtime is disposed: closing it early could send cached native bearer headers and the capability to an attacker reusing its port. Do not reroute directly or reactivate the failed route in place. Ordinary gateway errors and retries remain native and retain relay routing.

Normal disposal must first prove native runtime traffic and retries have stopped, then abort/drain streams with bounded cleanup, release the capability, close the relay, and close helper resources. A plugin dispose hook alone does not prove that ordering. If public lifecycle cannot guarantee it, the support gate fails; retaining a rejecting listener is required while native traffic can still exist, not an unbounded cleanup substitute. Failed setup may close an unpublished relay; per-request cancellation must not close the shared listener. Process termination/control-pipe EOF is a crash backstop, not proof of safe listener disposal. Do not install accumulating global shutdown handlers.

**Unresolved worker-death gate:** retaining the listener works only while the worker survives upstream/helper failure. Unexpected transport-child death releases its relay port even if the parent immediately invalidates the capability. Cached native requests/retries may already carry Authorization and the old capability and need not call `chat.headers` again; a new listener can receive those bytes without validating anything. Random capability, exit supervision, and parent header checks do not solve this. The desired contract is no usable stale route/capability and no native auth delivery after worker death, but it is not established. Evaluate a parent-owned stable numeric-loopback ingress guard that retains the native-facing port and rejects after worker loss, with a separately authenticated worker leg and safe upstream-port invalidation; worker transport remains separate. This is an architectural candidate, not an implemented or approved complete solution: forwarding races, parent disposal/death, native retry cessation, and bounded cleanup still need review/proof. Synthetic worker proof may proceed under isolated containment, but production activation/support remains gated on resolution; do not claim a full lifecycle guarantee.

### 6. Optional package boundary

Keep one default plugin export, bundle ordinary plugin code, and lazy-load only the reviewed optional bridge package when enabled. Pin an exact available bridge version/artifact and include its four helper assets and dependency notices through the upstream package, not hand-copied binaries. Default consumers must work when optional dependencies are omitted. Build/pack verification allows only this reviewed external import and optional dependency, replacing the blanket zero-import assertion without accepting arbitrary dependencies.

While upstream is unpublished, use a checksummed built local tarball for isolated development/verification. Do not commit machine-specific file dependencies or claim registry installation works. A publishable manifest requires an available exact upstream release; publication remains independently authorized. No install script, Go toolchain, root access, runtime helper download, or consumer-side build is allowed. Unsupported or missing helpers fail only the enabled bridge setup with a sanitized diagnostic.

### 7. Evidence before support claims

Keep existing bridge-disabled tests and packaged routing evidence intact. The existing isolated native-auth probe can support a standalone reverse-relay proof using synthetic credentials and loopback-only relay, forward-proxy, and gateway fixtures. This can verify native headers without parsing them in production; assertions inspect synthetic values only in the isolated probe. A standalone proof is not an implemented production relay or evidence of private capability injection. Record installed-host composition and capability secrecy/scoping as separate unchecked gates. Add deterministic bridge fakes and tests for original destinations, no direct retries, application/relay/proxy credential separation, TLS, redirects, Host/Origin/target abuse, missing capability, Connection nominations, SSE/tools, bounded backpressure, cancellation, concurrency, helper failure, and disposal ordering. No synthetic credential may reach a non-loopback endpoint.

Verify the installed tarball with optional dependencies both present and omitted, script-free installation, helper executable selection, license notices, and secret-free contents. Record exact OpenCode, embedded Bun, bridge revision/artifact digest, platform, and tests. Live enrollment and a real Aperture tailnet require separate explicit authorization and remain outside CI; no live result is inferred from mocks or upstream documentation.

## Risks / Trade-offs

- Direct fetch-adapter composition is absent at this pin; relay composition, private header injection/secrecy, private UI, and safe disposal remain unverified -> Keep feature implementation blocked pending explicit installed-host proofs.
- Bun 1.3.14 has a known streamed CONNECT upload regression -> Use explicitly selected verified external Bun for the worker now; test embedded mode negatively and accept future embedded candidates only after the same checks, never by semver alone.
- Persistent identity adds sensitive state and single-process locking -> Delegate upstream protections, document separate profiles, and require explicit safe deletion and remote revocation guidance.
- Relay capability and proxy URLs can leak via header/config/exception handling -> Prove closure-only injection and exercise config/provider APIs, logs, telemetry, persistence, and transcripts before support; report only allowlisted diagnostic categories.
- Loopback adds an application-credential trust boundary and port-reuse risk -> Authenticate requests, fix the upstream, retain a rejecting listener after failure, and prove traffic has stopped before normal closure. Same-user compromise remains outside protection.
- Optional dependency resolution and native assets complicate distribution -> Test installed tarballs with and without optional packages and preserve the reviewed-asset publication workflow.
- Startup retains native direct routing -> State this prominently in setup/failure documentation; do not promise network isolation.
